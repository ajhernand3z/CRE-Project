# Travis County CRE Comp Analysis

A commercial real estate comparable-sales analysis tool for Travis County,
Texas. Enter a subject property; it finds 5–10 comparables from the same
submarket, adjusts them for age and size differences, produces a
reliability-weighted valuation range, and asks Claude to write a
plain-English analyst summary grounded strictly in the comp data.

Built with **Python / FastAPI / SQLite / SQLAlchemy**, server-rendered
Jinja2 frontend, and the **Anthropic API** for the narrative layer.

## A note on the data (read this first)

**Texas is a non-disclosure state.** Sale prices are not public record —
neither TCAD's appraisal-roll export nor Regrid's parcel API carries actual
transaction prices for Texas parcels. This shapes the whole design:

- The `last_sale_price` / `last_sale_date` columns are nullable, and the
  valuation layer has an explicit fallback: a comp with no qualifying sale
  contributes its **TCAD appraised market value** instead, flagged in the
  UI ("appraised" badge) and penalized in the reliability weighting.
- The bundled demo dataset (`data/seed_comps.json`, 37 parcels) has
  **synthetic sale prices** generated by a documented model so the app runs
  end-to-end out of the box. Parcel characteristics are plausible for
  Austin; the prices are not real transactions.
- Cap rates are **pro forma estimates**: real NOI is never public, so it's
  modeled from market-level rent/vacancy/expense assumptions
  (`NOI_ASSUMPTIONS` in `app/config.py`) and labeled as such everywhere.

In a production setting the sale data would come from a paid source
(CoStar, CompStak, broker-verified comps); every schema field is already in
place for that.

## Quick start

Requires **Python 3.10+** (macOS ships an older 3.9 — install the current
version from [python.org/downloads](https://python.org/downloads) first).

```bash
pip install -r requirements.txt
python -m app.ingest.seed          # load the demo dataset into data/comps.db
uvicorn app.main:app --reload      # open http://localhost:8000
export ANTHROPIC_API_KEY=sk-...    # optional: enables the AI narrative
```

Try `Chicon St` with an asking price of `6500000`, or an unmatched subject:
`9999 Nowhere Ln`, industrial, 50,000 SF, built 2005, ZIP 78744.

Run the tests (24 hand-verified underwriting cases + integration tests):

```bash
python -m pytest tests/
```

## Loading real data

**TCAD certified export** (primary source): download the current certified
appraisal-roll export zip from
[traviscad.org/publicinformation](https://traviscad.org/publicinformation)
in a browser (the site sits behind a bot filter), then:

```bash
python -m app.ingest.tcad --file /path/to/certified_export.zip
```

The export is a zip of fixed-width files in the PACS "Appraisal Export"
layout (8.0.33 as of 2026). The loader reads the property table
(`APPRAISAL_INFO`, situs/values/state codes) and the improvement details
(building square footage as the sum of floor-type segments, plus year
built) in a streaming three-pass ingest — the offsets in
`app/ingest/tcad.py` were verified against actual 2026 export records.
Only commercial state-category codes (B1/B2/F1/F2) are ingested; a
delimited-file parser remains as a fallback for single-file exports.

**Regrid fallback**: with a Regrid API token:

```bash
export REGRID_API_TOKEN=...
python -m app.ingest.regrid --zip 78702 78704 78744
```

## How the underwriting math works

The full derivations are commented in `app/underwriting/adjustments.py`;
this is the summary a broker would ask for.

**1. Valuation basis.** Each comp contributes a price: its last sale if the
sale is within 24 months, otherwise TCAD's appraised market value (flagged
and down-weighted). A comp with neither is unusable and dropped.

**2. Age adjustment — +0.5% per year of age difference, capped at ±15%.**
Commercial buildings are underwritten on a 50–60 year economic life
(~1.7–2%/yr depreciation of *improvement* value), but a parcel's price
includes land, which doesn't depreciate, and buildings are maintained — so
the observable effect on total price is much smaller. A comp *older* than
the subject sold at a discount for its extra depreciation, so its price is
adjusted **up** to state it in subject terms; a newer comp is adjusted down.

**3. Size adjustment — elasticity −0.10, capped at ±10%.** Price per SF
falls as buildings get larger (thinner buyer pool, economies of scale).
Modeling `PSF ∝ SF^(−0.10)`, restating a comp's PSF at the subject's size
gives a multiplicative factor of `(comp_SF / subject_SF)^0.10` — a smaller
comp (which traded at a premium PSF) is adjusted **down** to the subject's
size, and vice versa.

**4. Reliability weighting — not a raw average.** Each comp's weight is
`1 / (1 + dissimilarity)`, where dissimilarity sums the absolute age and
size adjustment percentages, a staleness penalty of 5% per year since sale,
a 25% penalty for an appraised-value basis, and a 10% penalty when year
built is unknown. A near-identical recent sale therefore moves the answer
far more than a heavily-adjusted assessed value.

**5. Valuation range.** The indicated $/SF is the weighted mean of the
adjusted comp PSFs; the range is ±1 weighted standard deviation, times the
subject's square footage. If an asking price was entered, it's compared to
the midpoint and a pro forma cap rate is computed:
`NOI = SF × market_rent × (1 − vacancy) × (1 − expense ratio)`, cap = NOI /
price.

Every constant lives in `app/config.py` / the top of `adjustments.py` so an
appraiser can retune them, and `tests/test_adjustments.py` verifies the
math against hand-computed figures.

## The AI narrative layer

`app/narrative/generator.py` serializes the exact comp table — addresses,
raw and adjusted $/SF, adjustment percentages, weights, and search notes —
into the prompt and instructs the model to use *only* those figures, cite
specific numbers, name the most reliable comps, and flag weaknesses
(appraised fallbacks, stale sales). The narrative is commentary on the
tool's math, never a source of new numbers. If `ANTHROPIC_API_KEY` is
unset or the call fails, the results page renders everything else and shows
the reason instead.

## Project layout

```
app/
  config.py                 # data sources, submarket map, underwriting assumptions
  database.py, models.py    # SQLite via SQLAlchemy; one `properties` table
  ingest/
    tcad.py                 # TCAD certified-export parser (alias-mapped columns)
    regrid.py               # Regrid API fallback
    seed.py                 # bundled demo dataset loader
  underwriting/
    comps.py                # comp search: type / ±30% SF / submarket, widening rules
    adjustments.py          # the math (age, size, weighting, cap rates)
    analysis.py             # orchestration + subject resolution
  narrative/generator.py    # Anthropic API call
  main.py                   # FastAPI routes (HTML + /api/analyze JSON)
  templates/, static/       # server-rendered frontend
data/seed_comps.json        # demo dataset (synthetic prices — see note above)
tests/                      # 26 tests incl. hand-verified adjustment figures
```

## Deploying (free hosting on Render)

The repo includes `render.yaml`, so [Render](https://render.com) can deploy
it as a Blueprint: sign in with GitHub → New → Blueprint → pick this repo →
Apply. Set `ANTHROPIC_API_KEY` in the service's Environment tab to enable
the AI narrative (and set a monthly spend limit on your Anthropic account,
since the public form triggers API calls). Fresh deploys load the demo
dataset; to publish real TCAD data, build `data/comps.db` locally with the
ingest script and commit it with `git add -f data/comps.db`. Note the free
tier sleeps after inactivity — the first visit after a quiet period takes
~30 seconds to wake.

## Known limitations / next steps

- Submarkets are ZIP-code groupings (`app/config.py`) — coarse but
  transparent; a GIS layer would be the real upgrade.
- No time/market-conditions adjustment on sale prices (only a recency
  penalty in the weighting); appreciating older sales to present at a
  market rate would be a natural extension.
- Price-per-unit is computed only when unit counts exist (multifamily seed
  data has them; TCAD's export generally doesn't).
- The TCAD parser is built to the documented export structure but couldn't
  be run against a live export from the development sandbox (traviscad.org
  is unreachable there) — expect to add a column alias or two on first run.
